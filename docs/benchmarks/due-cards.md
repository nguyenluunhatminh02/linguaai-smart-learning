## 2. Exact query under test

`assertDeckAccess()` runs a separate `decks.findFirst` guard before the due-card query. It is a small indexed lookup (`decks.id` primary key) and is not the subject of this benchmark; record it separately if the runner measures the full HTTP path.

### Q1 — due cards (the primary query)

This is the SQL shape generated by the `user_card_progress.findMany` call at `srs.service.ts:35–48`: `user_id` equality, `next_review_date <= now`, join through `cards` with `deck_id`, `retired_at IS NULL`, and deck visibility (`creator_id = userId OR is_public = true`), ordered by `next_review_date ASC`, `take: limit`.

```sql
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
SELECT p.card_id, p.next_review_date, c.id AS card_row_id, c.deck_id, c.front_text
FROM user_card_progress AS p
JOIN cards AS c ON c.id = p.card_id
JOIN decks AS d ON d.id = c.deck_id
WHERE p.user_id = $1::uuid
  AND p.next_review_date <= $2::timestamptz
  AND c.deck_id = $3::uuid
  AND c.retired_at IS NULL
  AND (d.creator_id = $1::uuid OR d.is_public = true)
ORDER BY p.next_review_date ASC
LIMIT $4::int;
```

`$1` = fixture user UUID, `$2` = captured `now` timestamp, `$3` = fixture deck UUID, `$4` = limit (benchmark default: 20, matching the controller default). Source of `created_at`/`timestamp(6)` types: `apps/api/prisma/schema.prisma:446–464`. The `EXPLAIN` text must be captured verbatim, including the parameter values used, into the run evidence (see section 5).

### Q2 — learned-ID fallback

When Q1 returns fewer rows than `limit`, `srs.service.ts:50–69` first selects **all** progress rows for the user (`select: { card_id: true }`, no date or deck filter), then runs a `cards.findMany` with `id NOT IN learnedCardIds` for the remaining slots. These are two separate statements in the service; benchmark them separately.

```sql
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
SELECT card_id FROM user_card_progress WHERE user_id = $1::uuid;
```

```sql
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
SELECT c.id, c.deck_id, c.front_text
FROM cards AS c
JOIN decks AS d ON d.id = c.deck_id
WHERE c.deck_id = $3::uuid
  AND c.retired_at IS NULL
  AND c.id <> ALL($5::uuid[])
  AND (d.creator_id = $1::uuid OR d.is_public = true)
LIMIT $6::int;
```

`$5` = array of all learned card IDs for `$1` from the previous statement; `$6` = `limit - Q1 row count`. This mirrors the Prisma `notIn` shape; Prisma may implement the filter differently (for example `NOT IN (...)` with a literal list), so record the exact SQL emitted in the chosen harness. If the runner uses the Prisma query log instead of hand-written SQL, capture the generated SQL and bind parameters for each of the three statements and mark the method in the evidence field.

Cold-ish vs warm cache: define the procedure before running (for example a documented `pg_dropcache`-equivalent or database restart for cold-ish, and an identical immediately repeated run for warm), record the exact command and PostgreSQL settings (`shared_buffers`, `effective_cache_size`, `random_page_cost`, `work_mem`, `max_parallel_workers_per_gather`). A lab result is cold-ish, not true cold, unless the OS page cache is also controlled; say so in the evidence.

Interpretation rules:

1. A plan change is a fact only when both before and after EXPLAIN outputs are captured for the same dataset, parameters, and settings. A plan that merely looks better on paper is not evidence.
2. `Execution Time` from one `EXPLAIN ANALYZE` is one observation, not a p95. Report the number of runs and how p95 was computed; with no runs, keep `TBD`.
3. The composite index is useful only if it measurably reduces scan work or execution time **without unacceptable write and storage cost** at the measured scales. If the benefit appears only at 1M rows, say so; do not extrapolate to unmeasured scales.
4. If Q1 returns no rows due to filtering, the plan may be fast for the wrong reason. Record Q1 row count and confirm the fixture exercises both the due-card path and the fallback path.
5. The broad learned-ID `SELECT card_id ... WHERE user_id` (Q2 first statement) has a different shape from Q1. The candidate index may or may not affect it; report it as its own case, not as part of Q1.
6. DB-04 asks for write-impact and N+1 checks. A read-only improvement is not sufficient to promote the index into a migration.
7. PERF-01 SLO values are proposals for staging, not proven capabilities. This document does not declare pass/fail against them.
